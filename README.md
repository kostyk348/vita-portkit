# vita-portkit — инструменты переноса ПК-игр на PS Vita

Цель: универсальный конвейер **x86_64 → ARM32 (PS Vita)** + переиспользуемая обвязка.

## Что уже проверено (факты)

| Слой | Статус | Доказательство |
|---|---|---|
| x86 → IR → SSA | ✅ работает | `sdre` лифтит реальные функции |
| IR → ARM32 emit | ✅ работает | `sdre --target arm` даёт настоящий ARM asm |
| ARM-ассемблер без кросс-тулчейна | ✅ работает | `clang --target=armv7-linux-gnueabihf -fuse-ld=lld` |
| Исполнение/верификация ARM | ✅ работает | `qemu-arm` (exit=42 на тесте) |
| **Семантика трансляции** | ✅ **верифицирована исполнением** | `verify_func.sh v.c add3 5 7 15` → exit=15 ✅; `mul5 9` → exit=45 ✅ |
| **`lea` с масштабом** | ✅ сделано | `mul5` → `add r1, r0, r0, lsl #2` — x*5 в ОДНОЙ инструкции (лучше оригинала!) |
| SIMD (SSE → NEON) | ❌ нет | `movdqu/paddd` → комментарии |
| Флаги (CF/OF/SF/ZF) | ⚠️ частично | `test/cmp` без точной семантики |
| ABI (аргументы/возврат) | ✅ **сделано** | `Value::Input` (rdi/rsi/rdx/rcx/r8/r9) пиннятся на r0–r5; возврат в r0 |
| Рантайм (syscalls, malloc, threads) | ❌ нет | — |
| Платформенный шим (SDL2/GL/audio/input) | ❌ нет | — |
| vitaSDK | ❌ не установлен | `~/vitasdk` = только `vdpm` (нужен toolchain ~1 ГБ) |

## Архитектура (что должно получиться)

```
  [x86_64 ELF] --sdre--> [IR/SSA] --emit_arm--> [ARM32 asm]
        |                                            |
        |                                      [clang/lld]
        v                                            v
   данные/ресурсы                            [ARM32 ELF]
   (ftl.dat -> unpack_pkg)                          |
        |                                     +------+------+
        v                                     |  РАНТАЙМ    |  syscalls -> SceKernel
   [ftl_unpacked/]                            |  malloc     |  threads  -> SceThread
                                              |  fs         |
                                              +-------------+
                                                    |
                                              +-------------+
                                              |  ШИМ (SDL2) |  GL -> GLES2 (SceGxm)
                                              |  audio      |  SceAudio
                                              |  input      |  SceCtrl
                                              +-------------+
                                                    |
                                              [VPK для Vita]
```

## Этапы

**Ф1 — транслятор целых функций.** ✅ `lea` со масштабом сделан (→ одна ARM-инструкция).
Осталось: точные флаги (CF/OF/SF/ZF), ABI (входные регистры, стек-фрейм для -O0 кода,
вызовы функций). Верификация: `verify_func.sh` (x86 → ARM → qemu-arm → сверка exit-кода).

**Ф2 — SIMD.** SSE → NEON (ARMv7 NEON 128-бит): `movdqu/paddd/mulps` → `vld1/vadd/vmul`.

**Ф3 — рантайм.** Linux syscalls (`mmap/brk/open/read/clock_gettime`), malloc,
pthread → SceThread, файлы → наш `unpack_pkg` (данные игры читаются прямо из архива).

**Ф4 — платформенный шим.** `SDL2 + OpenGL` → `SDL2(vita) + GLES2 + SceAudio + SceCtrl`.
Переиспользуется всеми портами (это и есть "универсальная обвязка").

**Ф5 — пилот.** Сначала 32-битная цель (у 32-бит x86 указатели 4 байта → нет проблемы
64→32), затем более крупные.

## Главные риски (честно)

1. **64 → 32 бита.** FTL Linux — `x86_64` (указатели 8 байт), Vita — ARMv7 (4 байта).
   Варианты: (а) брать 32-битную сборку цели (у FTL есть Windows x86 `FTL.exe`);
   (б) эмулировать 64-бит (×2 медленнее). Рекомендация: **32-битные цели**.
2. **Производительность.** Cortex-A9 @444 МГц; транслированный код ×2–4 медленнее.
   2D-игры (FTL) — шанс есть, 3D — вряд ли.
3. **Прецеденты на Vita — source-порты**, не бинарная трансляция: re3/reVC (GTA),
   Sonic Mania, Ship of Harkinian. Т.е. реверс → реимплементация на C → нативная сборка.
   Бинарная трансляция x86→Vita — territory без готовых решений (это наш research).

## Замеры: коэффициент расширения x86 → ARM (AOT)

Трансляция **до запуска** — runtime-налога нет (никакого JIT/интерпретатора).
Но транслированный код **длиннее** оригинала (измерено `ratio2.sh`):

| функция | x86 инстр. | ARM инстр. | коэффициент |
|---|---|---|---|
| `mul5(x)=x*5` | 2 | 3 | ×1.50 |
| `f3(a,b,c)=a*100+b*10+c` | 5 | 6 | ×1.20 |
| `checksum(p,n)` (цикл) | 20 | 24 | ×1.20 |
| `find_max(a,n)` (цикл+ветвление) | 17 | 25 | ×1.47 |
| `add3(a,b)=a+b+3` | 2 | 4 | ×2.00 |

**Почему код длиннее** (это и есть источник просадки, а не «трансляция во время работы»):
1. **Флаги.** x86 ставит CF/OF/SF/ZF почти на каждой ALU-операции; ARM — только NZCV и не
   на всех. Если флаги читаются позже — их нужно материализовать (лишние инструкции).
2. **Регистры.** x86_64: 16 GPR; ARM32: 13 (r0–r12, плюс sp/lr/pc). Нехватка → спиллы в память.
3. **Разложение сложных инструкций** (`imul` с памятью, строковые `rep movs`, x87) — 1:N.
4. **64→32 бита** (если цель x86_64): указатели 8 байт → либо 2 регистра, либо «тонкие» указатели.
5. **Кэш.** Код больше → промахи L1I (32 КБ на Cortex-A9).

## Стоимость КАЖДОЙ команды (Cortex-A9) — главное

Латентности в тактах у ARM и x86 **сопоставимы** (ALU 1 такт, LDR ~4, MUL ~3):

| команда | Cortex-A9 (Vita) | десктопный x86 | комментарий |
|---|---|---|---|
| ALU (add/sub/and/orr/mov+cдвиг) | **1 такт**, до 2 за такт (dual-issue) | 1 такт, 4–6 за такт | ARM делает больше за инструкцию (сдвиг в операнде!) |
| LDR/STR (L1) | issue 1, latency ~4, ~2 за такт (1 LSU) | latency 4–5, 2–3 за такт | сопоставимо |
| MUL (32×32) | latency **3**, throughput 1 | latency 3, throughput 1–2 | сопоставимо |
| DIV | **~20+ тактов** | ~20–40 | дорого у обоих |
| B/BL | 1 такт + **штраф ~8–10** за промах предсказания | 1 + ~15 | сопоставимо |
| NEON (128-бит: vadd/vld1) | 1–2 такта (4×int32 за раз) | SSE: 1 такт (4×int32) | сопоставимо по работе |

**Значит дело не в «медленности команд», а в трёх множителях:**
1. **IPC:** A9 выдаёт ≤2 инструкции/такт (реально 1.2–1.5), десктоп 4–6 (реально 2–3)
   → **~2×** меньше работы за такт.
2. **Частота:** 444 МГц против ~3.5 ГГц → **~8×**.
3. **Расширение кода:** ×1.2–1.5 (замерено).

**Итого: ×(2 · 8 · 1.3) ≈ ×20–35 медленнее** для той же работы.

### Замер на наших функциях (cycles_estimate.py, модель A9)

| функция | ALU | LOAD | BRANCH | тактов (нижняя / реалистично) |
|---|---|---|---|---|
| `add3` | 3 | 0 | 1 | 3 / 7 |
| `mul5` | 2 | 0 | 1 | 2 / 6 |
| `checksum` (цикл) | 19 | 1 | 4 | 15 / 33 |
| `find_max` (цикл) | 18 | 2 | 3 | 14 / 30 |

Пример: итерация `checksum` — x86 ~20 инстр ≈ 5–7 тактов десктопа (≈2 нс при 3.5 ГГц);
на Vita 24 ARM-инстр ≈ 15–33 такта (≈34–74 нс при 444 МГц) → **~17–35×**.

### Почему это не приговор для 2D-игр

Транслируется только **CPU-логика**. Рендер/звук/ввод идут через шим в **нативные**
Vita-API (GLES2 → GPU SceGxm, SceAudio, SceCtrl). GPU делает тяжёлую работу сам.
Для FTL (2D, лёгкая логика) бюджета кадра (16.7 мс при 60 FPS ≈ 7 Млн инструкций
на 444 МГц) скорее всего хватит; для 3D — нет.

**Вывод:** брать **32-битную цель** (тогда п.4 исчезает и расширение меньше), и ожидать
просадку в основном из-за частоты CPU, а не из-за трансляции.

## Что ещё не работает (честно, с примерами)

- **`imul r,r,imm` в цепочках** — SSA путает операнды: `f3(a,b,c)=a*100+b*10+c`
  транслируется неверно (exit=1 вместо 123). Причина: порядок входов для
  переопределяемого регистра (`imul edi,edi,imm`) в SSA-резолвере.
  Локация: `sdre/src/ssa.rs` (резолв входов) + `adapter/x86.rs:311` (alu_2op).
- **Стек-фреймы (`-O0`)** — нет ABI-слоя для rbp/rsp (падение). Нужно: выделение
  кадра, отображение `[rbp±N]` → ARM-стек.
- **Флаги (CF/OF/SF/ZF)** — `cmp/test` без точной семантики → условные переходы
  могут быть неверны для multi-byte/overflow случаев.
- **SIMD (SSE→NEON)** — не сделано (movdqu/paddd → комментарии).
- **Вызовы функций** — `call` → нужен `bl` + сохранение/восстановление регистров.

## Порядок работ (обновлён)

1. ✅ `lea` с масштабом → одна ARM-инструкция.
2. ✅ ABI-пиннинг аргументов (rdi→r0 … r9→r5), возврат в r0.
3. ⏳ **резолв входов SSA** (imul/lea-цепочки) — блокер для сложных функций.
4. ⏳ стек-фреймы + вызовы (call/bl, сохранение регистров).
5. ⏳ флаги (CF/OF/SF/ZF).
6. ⏳ SIMD SSE→NEON.
7. ⏳ рантайм (syscalls/malloc/threads) — независим от 3-6, можно параллельно.
8. ⏳ платформенный шим SDL2/GL → GLES2/SceAudio/SceCtrl.

## Быстрый старт

```bash
./verify_pipeline.sh test.c my_func             # показать конвейер
./verify_func.sh v.c add3 5 7 15                # верификация: x86 -> ARM -> qemu-arm (✅ exit=15)
./verify_func.sh v.c mul5 9 0 45 1              # вторая функция: x*5 (✅ exit=45)
```

## Результаты верификации (факты)

```
$ ./verify_func.sh v.c add3 5 7 15
    add r2, r0, r1
    add r2, r2, #3
    mov r0, r2  @ return value
    bx lr
exit=15, ожидалось 15
✅ ТРАНСЛЯЦИЯ ВЕРНА

$ ./verify_func.sh v.c mul5 9 0 45 1
    add r1, r0, r0, lsl #2     <- x*5 одной инструкцией ARM
    mov r0, r1  @ return value
    bx lr
exit=45, ожидалось 45
✅ ТРАНСЛЯЦИЯ ВЕРНА
```

Найденное ограничение: код `-O0` (со стек-фреймом) требует ABI-слоя — на нём падает
(нужен стек/фрейм). Код `-O1` транслируется и исполняется корректно.
